# 代码坏味道清单（Code Smells）

> 用于 AI 在筛查代码时识别坏味道并给出修复建议。脚本只做定量检测，坏味道的定性判断依赖本清单 + 上下文。

## 一、臃肿类（Bloaters）

| 坏味道 | 识别标准 | 修复手法 |
|--------|---------|---------|
| 长函数（Long Method） | 函数超过约 30–50 行，职责混杂 | 提取子函数（Extract Method） |
| 大类（Large Class） | 类字段/方法过多，职责过多 | 提取类（Extract Class）、按职责拆分 |
| 长参数列表（Long Parameter List） | 参数超过 3–4 个 | 引入参数对象（Introduce Parameter Object） |
| 数据泥团（Data Clumps） | 多个参数/字段总是一起出现 | 合并为对象/结构体 |
| 基本类型偏执（Primitive Obsession） | 用字符串/数字表示本应有类型的概念 | 引入值对象/枚举 |

## 二、工具滥用（Tool Abuses）

| 坏味道 | 识别标准 | 修复手法 |
|--------|---------|---------|
| 过度注释（Comments） | 大量解释"做了什么"而非"为什么"的注释 | 用清晰命名替代，只保留"为什么"注释 |
| 重复代码（Duplicated Code） | 多处逻辑高度相似（脚本 `find_duplicates.py` 可检出） | 提取共享函数/模板方法 |
| 神秘命名（Mysterious Name） | 变量/函数名无法表达意图（如 `data`、`tmp`、`foo`） | 重命名为意图揭示的名字 |

## 三、变更预防（Change Preventers）

| 坏味道 | 识别标准 | 修复手法 |
|--------|---------|---------|
| 发散式变化（Divergent Change） | 同一类因不同原因频繁变化 | 按变化维度拆分类 |
| 霰弹式修改（Shotgun Surgery） | 改一个概念要在多处做相同小改 | 把相关逻辑聚拢到一处 |
| 平行继承体系 | 每加一个类都要对应加另一个类 | 合并或引入工厂 |

## 四、可有可无（Dispensables）

| 坏味道 | 识别标准 | 修复手法 |
|--------|---------|---------|
| 死代码（Dead Code） | 从未被引用的函数/类/变量（脚本 `detect_dead_code.py` 可检出） | 删除（需确认） |
| 无用注释/僵尸代码 | 大段被注释掉的旧代码 | 删除，依赖版本控制回溯 |
| 重复数据 | 多处维护同一份数据 | 单一数据源 |
| 过度设计 | 为不存在需求预留的抽象/接口 | 简化，按需实现 |

## 五、耦合（Couplers）

| 坏味道 | 识别标准 | 修复手法 |
|--------|---------|---------|
| 特性依恋（Feature Envy） | 方法大量使用别的类的数据 | 移动方法到数据所属类 |
| 不恰当的亲密关系 | 类间互相访问私有成员 | 收窄可见性、重建边界 |
| 中间人（Middle Man） | 类只是简单委托，自己没逻辑 | 移除中间层 |

## 六、其他常见问题

| 坏味道 | 识别标准 | 修复手法 |
|--------|---------|---------|
| 深层嵌套 | if/for 嵌套超过 3–4 层 | 提前返回（Guard Clause）、提取函数 |
| 魔法数字（Magic Number） | 直接出现的无说明数字字面量 | 提取为具名常量 |
| 重复条件分支 | 相似 if-else 结构反复出现 | 多态/查表法替代 |
| 不恰当命名 | 中英混用、缩写难懂、`a`/`b`/`x` 等无意义名 | 统一命名规范，见 `language-rules.md` |
| 过长链式调用 | `a.b().c().d().e()` 过度链式 | 引入中间变量、拆分 |

## 判定原则

1. 坏味道是"候选信号"而非"必然缺陷"——需结合上下文（性能要求、团队约定、框架惯例）判断。
2. 优先报告**高置信度**问题；不确定的用"建议"级别而非"警告/严重"。
3. 每个坏味道都要给出**具体的修复手法**和**示例**，而非空泛建议。
